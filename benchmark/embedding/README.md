# Does the embedding stage earn its place?

One question, asked against runs the crawler actually did: **for the
candidates it sees today, does ranking by embedding put the relevant ones
first — better than the rule ranker alone, and by enough to pay for
itself?**

The old benchmark answered a version of this and its answer stopped
being about the current system. It scored 300 hand-labelled candidates
whose only text was a link's business card: anchor, snippet, heading.
Feed candidates arrive carrying the post itself, which is a different
input to the same model, and the labelled set could not grow with the
crawler. This one is built so it never goes stale.

## Where the labels come from

**The analyzer.** A run made with `--recall` removes nothing: the
embedding stage turns its top-K into an ordering instead of a cut, so
every candidate is fetched and analysed, including the ones it would
have dropped. What comes back is, for each candidate:

- the text the candidate carried at ranking time (`links.text`)
- the verdict the analyzer reached after reading the page
  (`analyses.classification`, backed by evidence it checked)

That is a labelled set, generated by running the product, refreshed
every time it runs, and free of hand-labelling drift.

**What it is not:** gold. The analyzer is the system's own judgement,
not a human's. It is the right target anyway, because the question is
"does the cheap stage order things the way the expensive stage would" —
the expensive stage is the standard being approximated.

**The one thing that must not be skipped:** the run has to be
`--recall`. Scored on an ordinary run, this measures only the candidates
that survived, which is 78% relevant by construction, and every ranker
looks equally good on survivors. Measuring survivors was how a first
attempt at this made the embedding stage look useless.

## What it reports

For each configuration, over the same candidates:

| Metric | Question it answers |
|--------|--------------------|
| AP | Are relevant candidates near the top overall? |
| precision@k | Of the first k fetched, how many were worth it? |
| recall@k | Of everything relevant, how much does a cut at k keep? |
| relevant lost per fetch saved | The actual trade: cutting at k saves fetches and costs results |

Configurations compared:

- **rule only** — the baseline the embedding stage has to beat
- **embedding** at the model's real token ceiling and at the shipped one
- **rule+embedding blend**, at the weights the pipeline uses

The token ceiling is worth its own column because it is not what it
looks like: `_MAX_EMBED_CHARS` is measured in characters, the model
truncates in tokens, and the shipped model's tokenizer cuts at 128 of
them — about 447 characters. A 1,200-character caption reaches the model
as its first third.

## What it found the first time it ran properly

On a 120-page `--recall` run over four release feeds, split the way the
report splits it:

| | candidates | relevant | rule AP | embedding AP |
|---|---|---|---|---|
| carrying their own text | 38 | 37% | **0.884** | 0.769 (0.855 at 512 tokens) |
| ordinary links | 130 | 7% | 0.132 | **0.297** |
| both together | 168 | 14% | 0.124 | 0.590 |

Three things worth keeping:

- **The mixed row is a trap.** It says embedding beats the rule ranker
  five to one. Split, the rule ranker wins on candidates that carry
  text and loses on the ones that do not, and the mixed number is just
  the two groups in unequal proportion.
- **Each stage earns its place somewhere different.** A candidate that
  states its own text is matched well enough by keywords, which cost
  nothing; a bare link has only its URL and anchor, and that is where a
  semantic model has something to add.
- **Raising the ceiling to 512 tokens does not pay.** It is the only
  group whose text exceeds 128 tokens, and there the extra reading moved
  AP from 0.769 to 0.855 — still below the rule ranker — for about five
  times the compute per candidate.

**Missing from those numbers:** `recency`, a quarter of the feed factor
set. `posted_at` was not written to the `links` table when that run
happened, so its rule score came from `text_match` alone. Runs made
after 2026-08-22 carry it, and are not directly comparable to the table
above.

**And read the table as one task, not as a verdict.** "Release
announcements" is a job keywords are unusually good at: the goal says
`release notes`, `changelog`, `version`, and the relevant entries are
titled "Python 3.13.9 is now available". Against 2,000 random orderings
the rule ranker's 0.884 beat every one of them, so it is real -- but a
goal whose words do not appear in the text it is looking for ("what is
new at bubble tea shops", against a post titled "GRAPE News") is the
case that would separate the two stages, and it has not been run yet.

## Running it

```bash
# Everything at once, including the two scorings:
./benchmark/embedding/run.sh --pages 120

# A walled platform needs a session.  Pass the path; nothing is stored here.
./benchmark/embedding/run.sh --session ./ig-session.json --seeds ./accounts.json \
  --prompt "<what you are looking for, naming the fields you want>"

# Or by hand:
# 1. A run that removes nothing.  Costs a full crawl of LLM budget.
crawl run "<prompt>" --seeds "..." --recall --page-budget 120

# 2. Score every candidate in it, offline, no LLM, no re-crawl.
python benchmark/embedding/score.py results/<run-id>
python benchmark/embedding/score.py results/<run-id> --max-tokens 512
```

`score.py` re-embeds from the stored candidate text, so sweeping a
setting costs one local model pass and never touches the network.
